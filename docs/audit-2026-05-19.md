# Quality audit — Marketing Analytics Pack v0.2.0

**Date:** 2026-05-19
**Scope:** All 27 commands, 27 skills, 3 advanced runners, shared style system, validator, README/CHANGELOG/CONTRIBUTING, examples and sample data.
**Method:** Read every command and skill end-to-end; ran `scripts/validate.py`; smoke-tested the RFM runner against `examples/data/orders.csv`; spot-checked the Prophet and Meridian runners' top sections, dep handling, and arg parsing; cross-referenced commands ↔ skills ↔ examples for completeness; checked frontmatter, naming, and `Use skill:` resolution.

---

## TL;DR

The pack is in materially good shape for v0.2.0. Structure is consistent, marketplace invariants pass cleanly, marketing-domain literacy is strong, and the advanced runners are real working code with sensible install handling. The gaps that matter are concentrated in three places:

1. The shared `data-visualization` reference skill only ships three chart patterns (bar, line, h-bar), while skills downstream reference chart types it doesn't define (waterfall, scatter, Venn/matrix, multi-line response curves, fan/interval). Either add patterns, or relax the "don't invent chart styling locally" rule.
2. A small set of the leaner skills (60–75 lines) feel under-developed next to the richer ones (KPI tree, root cause, churn driver, CLV). They are correct but generic; they don't carry the worked-method library that lets Claude give tailored output for a non-technical user.
3. Small consistency drift: `check-data` has no worked example, `main-analysis-planner`'s intent table doesn't use slash-command names, two `CONTRIBUTING.md` files exist (root + `docs/`), and the v0.2.0 "Planned" CHANGELOG block lists items that have shipped.

None of these block shipping or marketplace submission. They're the difference between v0.2.0 and a polished v0.2.1.

## Findings, severity-ranked

### HIGH — gaps that affect user experience

#### H1. `data-visualization` reference skill only defines three chart patterns

`skills/data-visualization/SKILL.md` contains: style loading, matplotlib rc setup, **bar**, **line**, **horizontal bar**, plus number-formatting helpers. The rule it states is:

> Use this reference skill whenever a command creates a chart. **Do not invent chart styling locally.**

But several downstream skills reference chart types that aren't in the reference:

| Skill | References chart type | In reference? |
|---|---|---|
| `audience-overlap-visualiser` | "matrix/bar/Venn-style summary" in output template | matrix/Venn **no** |
| `suppression-waterfall-builder` | "waterfall chart or ranked removal bar chart" | waterfall **no** |
| `rfm-segment-generator` | Recency vs Frequency **scatter**, bubble size = monetary | scatter **no** |
| `mmm-runner` | multi-line **response curves** per channel | multi-line **no** |
| `forecast-runner` | actuals + forecast + 80% CI **fan / interval** chart | interval **no** |
| `mmm-result-interpreter` | discusses contribution / ROI / response curves | none defined |

The runner scripts work around this by writing matplotlib inline (RFM script ships its own `plot_rf_scatter` and `plot_segment_sizes`; Prophet/Meridian scripts similarly), which is fine — they read tokens from `lib/visualize.py`. But the **skill-level claim** that chart styling is reused is partially true; for the non-runner skills that want to render a waterfall or Venn, Claude has nowhere to copy from.

**Fix options:**
1. Add the missing chart patterns to `data-visualization/SKILL.md`: scatter, multi-line (with optional shaded interval), simple waterfall (bar + delta colouring), simple overlap matrix. ~80–120 extra lines. Highest leverage — unlocks consistent visuals across the segmentation, marketing-ops, forecasting, and MMM clusters.
2. Or split into `data-visualization` (general patterns) plus narrower `chart-waterfall`, `chart-scatter`, `chart-interval` skills if you want to keep the reference lean.
3. Or weaken the rule to "prefer reference patterns where available; otherwise follow the style loading + axis setup conventions". Cheapest but loses some of the visual-consistency story.

Recommendation: option 1, in v0.2.1.

#### H2. `/check-data` has no worked example

26 of 27 commands have an `examples/<command>-example.md`. `check-data` does not — even though it's a front-door command and the data-readiness story is one of the pack's main pitches in the README. Easy fix; should reuse one of the existing sample CSVs (e.g., `examples/data/mmm-weekly.csv` "is this enough for an MMM run?" or `examples/data/orders.csv` "can I build RFM from this?") so the example doubles as a flow demo.

#### H3. Two `CONTRIBUTING.md` files

- `CONTRIBUTING.md` at the repo root — 113 lines, current, well-written.
- `docs/CONTRIBUTING.md` — 93 lines, older draft. Different content, not a redirect.

`CLAUDE.md` and `URB-182` previously noted "CONTRIBUTING.md referenced but not in repo" — that's been fixed at the root, but the older `docs/CONTRIBUTING.md` was left behind. Delete it (or replace with a one-line forward to `../CONTRIBUTING.md`).

### MEDIUM — quality gaps that affect skill output

#### M1. `main-analysis-planner` Intent Classifier uses prose names, not slash commands

The table in `skills/main-analysis-planner/SKILL.md` has rows like:

```
Root cause diagnosis    | "Why did X drop?"       | Root cause investigation tree
Segmentation            | "Group customers"       | Segmentation method selector
RFM                     | "best customers"        | RFM segment generator
Experimentation         | "A/B test"              | Experiment design reviewer or incrementality test designer
```

The skill's workflow says "Name the command to run", and the companion `plan-analysis` command's Routing Map uses real slash commands (`/root-cause-tree`, `/segmentation-method`, `/incrementality-test-designer`, etc.). The intent table should match. Otherwise Claude will pick up "Root cause investigation tree" as the routing string and the user has to translate.

Fix: rewrite the Best route column to use slash commands. ~10 minutes.

#### M2. Lean skills under-developed vs. rich ones

Compare line counts (and worked-method depth):

| Rich (have decompositions / examples / common patterns) | Lean (table + template + guardrails only) |
|---|---|
| kpi-tree-generator (146) | segmentation-method-selector (68) |
| root-cause-investigation-tree (129) | forecast-method-selector (66) |
| clv-scenario-modeller (148) | attribution-model-selector (67) |
| customer-journey-measurement-framework (140) | audience-overlap-visualiser (68) |
| churn-driver-narrative-generator (79 + 5 common-pattern block) | frequency-cap-fatigue-analyser (68) |
| campaign-post-mortem-generator (95 + 5 common-pattern block) | mmm-result-interpreter (68) |

The rich ones give Claude priors — formula libraries, branch templates, common-pattern lists, business-model variants. The lean ones give Claude just "here's a method table, pick one". For a non-technical user that's the difference between a tailored output and a generic recommendation that reads like a textbook entry.

Highest-leverage skills to enrich:

- **`mmm-result-interpreter`** — most senior signal in the pack. Should include common interpretation traps (carryover vs saturation confusion, base/trend stealing media credit, marginal-ROI being spend-dependent, KPI sensitivity), plus a worked "good vs bad MMM readout" pair.
- **`experiment-design-reviewer`** + **`incrementality-test-designer`** — should at least mention sample-size / minimum detectable effect directionally. They are the most common asks in this cluster.
- **`segmentation-method-selector`** — should carry 2–3 worked recommendations (e.g. "ecommerce with 6 months of orders, no events → start with RFM, not clustering") to mirror what kpi-tree-generator does for KPI trees.
- **`attribution-model-selector`** — should explicitly walk through the attribution-vs-incrementality distinction with a worked decision (it has a "If You Need Incrementality" output slot but no examples).

#### M3. `/style` command relies on hand-editing `custom.yaml`

The workflow says "copy the closest bundled style and changing only the supplied brand fields". `lib/styles/custom.yaml` is shipped as a clone of `default.yaml`, so the brand block is already there. But the actual file mutation is left to Claude — there's no script and no skill convention for "how to safely write to custom.yaml". In Cowork / Claude Code this works because of file tools; in pure web chat it doesn't. Mirror the runner pattern: either add a tiny `lib/set_brand.py` (3-arg CLI: hex, logo, font) or make the `/style` skill explicitly stamp out the YAML block with hex/logo/font interpolated and tell Claude to overwrite the file.

#### M4. `default.yaml` font is "Arial" which doesn't exist on Linux

Smoke test of the RFM runner produced ~27 "findfont: Font family 'Arial' not found" warnings before falling back to DejaVu. The charts still rendered correctly, but the warnings make the runner output look broken to a non-technical user reading the console. Suggested fix: change `brand.font_family` default to `"DejaVu Sans"` (matplotlib-bundled, exists everywhere), keep "Arial" as a typical custom override.
